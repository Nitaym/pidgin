Feature Spec

Change-Gated Wakeup

A recurring self-wakeup runs its expensive turn only when a cheap, DB-only probe shows something actually changed since that timer last ran — otherwise it skips.

Draft Author: Nitay 2026-07-06

1Summary

The autonomy layer arms recurring timers (daily/weekly/interval) that wake an agent on a fixed cadence — including high-frequency pollers that fire every 30 minutes. Today every fire builds a full LLM turn even when the world is unchanged, burning tokens, drawing down the daily wakeup budget, and adding noise to the operator's dashboard. Change-Gated Wakeup keeps the heartbeat cadence but inserts a cheap gate before the turn is built: a pure-DB probe over five change sources, compared against the timer's own last real run. If nothing qualifying has changed, the wakeup ends immediately as a recorded skipped turn — no LLM call, no budget draw — and re-arms as usual. A configurable set of guaranteed daily wake times (default one at 09:00) stays ungated so every agent still does a full pass on a floor cadence even in a totally quiet world. Every skip is auditable, carrying the exact probe snapshot that justified it.

2Scope

In scope

  • A change probe: a cheap, read-only, DB-only check over five change sources, run before a recurring wakeup builds its turn.
  • Gating of all recurring timers uniformly — skip the LLM turn when the probe finds nothing changed.
  • A per-timer baseline (last_ran_at) that only advances on a real, non-skipped run.
  • Recorded skipped turns with a probe snapshot, surfaced (collapsed) in the agent turn dashboard.
  • A guaranteed daily wake-times floor (ungated), armed at bootstrap; default a single 09:00.
  • A per-agent Advanced configuration panel exposing the knobs, plus a per-timer always_run opt-out.
  • Excluding skips from max_wakeups_per_day, documented at the counter.

Out of scope

  • Connector-side watcher push (trigger-5 real-time delivery) — the probe only reads change rows others record; it does not build them.
  • Gating non-recurring wakeups: bootstrap, one-shot self-prompts, supervisor reports, and external triggers (1–3, 7, 8) are never gated.
  • Active polling of connectors at probe time — the probe makes no network calls.
  • Changing the recurrence engine, re-arm math, or the trust model (all unchanged from the autonomy spec).
  • Any global "bring empty wakeups back" switch — the gate is safe by construction; only per-agent tuning exists.

3Why this exists

The autonomy layer made agents self-running: they arm their own recurring timers and wake on a cadence with no human in the loop. A common shape is a short-interval poller — "check the campaign every 30 minutes." That's ~48 firings a day from one timer, and in a quiet hour every one of them builds a full LLM turn to look at an unchanged world, conclude there's nothing to do, and go back to sleep.

Three concrete costs of an empty wakeup that still runs:

  • Token/compute cost — a full context-assembly + LLM turn for a no-op.
  • Budget starvation — the autonomy spec caps max_wakeups_per_day at 100; a 30-minute poller alone can eat half of it doing nothing, deferring the agent out of real work.
  • Dashboard noise — the turns timeline fills with identical "nothing to do" turns, burying the ones that mattered.

The runtime already knows how to record that something happened — new inbound_events rows, tasks_status_log entries, resolved approvals, fired watchers, delegated returns. What's missing is a cheap gate that consults those records before paying for a turn, so the cadence stays as a heartbeat but only cashes out into real work when there's work to do.

4How it works

4.1 The gate in the turn lifecycle

Nothing changes about how a recurring timer fires. It still materializes as an inbound_events row (trigger_type = 'timer', processing_status = 'pending'). The gate sits in the worker, between claiming the row and building the turn: 

recurring timer fires -> inbound_events row (pending)
  worker claims row
    run change probe (pure DB, read-only, no LLM, no network)
      gating disabled for agent?  -> RUN
      timer.always_run = 1?       -> RUN
      any source count > 0?        -> RUN
      else                        -> SKIP

    RUN:  dispatching -> build turn -> LLM -> done
          stamp timer.last_ran_at = now   (advances baseline)
          draws 1 against max_wakeups_per_day
          re-arm recurrence

    SKIP: create turn record (status = skipped, + probe snapshot)
          inbound_events.processing_status = skipped
          DO NOT stamp last_ran_at   (baseline unchanged)
          DOES NOT draw against the wakeup budget
          re-arm recurrence exactly as a normal fire would

4.2 What counts as "changed" — the five sources

The probe counts qualifying rows for each source since this timer's last_ran_at. The change signal is the union of all five; any single non-zero count runs the turn.

#SourceProbe reads
1New inbound eventsinbound_events for this agent with received_at > last_ran_at (DMs, channel activity, external mail).
2Task state changetasks_status_log entries since baseline (new/unblocked), plus tasks whose due_at crossed the last_ran_at → now window (computed).
3Approvals resolvedpending_approvals for this agent resolved since baseline.
4Watched-resource changeFired agent_watchers / watcher inbound_events since baseline — only for resources the agent explicitly watches, never ambient connector activity.
5Delegated returnsPeer-delegation results routed back to this agent since baseline.

Source 4 is scoped to explicit watchers only. A file changing somewhere in a shared Drive is not a wakeup reason. It counts only if the agent set up (or was told to set up) an agent_watchers subscription on that resource — matching trigger-5's meaning, "something you were keeping an eye on changed." Otherwise a busy shared Drive would defeat the gate.

4.3 The baseline: this timer's own last real run

Each recurring timer carries last_ran_at — the timestamp of its most recent non-skipped turn (null on first fire). The probe always asks "anything since my last_ran_at?" Two rules make this safe:

  • Skips never advance the baseline. If a 30-min timer skips at 09:00 and 09:30, then a watched file changes at 09:45, the 10:00 fire compares against the last real run (say 08:30), sees the change, and runs. Changes accumulated across a quiet streak are never swallowed.
  • Other timers and triggers don't advance it. A direct-address turn at 09:50 does not let the 10:00 review skip — the review has its own job the DM didn't do. Errs toward running (the safe direction).

4.4 Which wakeups are gated

WakeupGated?Why
Recurring timers (all cadences)YesThe only clock-driven polls that find an empty world. In practice only the frequent ones ever skip — a daily/weekly review almost always has some change.
Guaranteed daily wake timesNoThe floor. Always a real pass (see 4.5).
BootstrapNoMust run; no last_ran_at to compare against.
One-shot self-promptNoA deliberate future commitment ("remind me Friday to X"), not a poll.
Supervisor reportNoFires as a liveness heartbeat even in a quiet week; a quiet probe just makes it a one-liner.
Direct address / inbound / delegation / approval (1,2,3,7,8)NoThese are the change — something already happened.

4.5 The guaranteed-wake floor

To prevent an agent going silent for days when nothing changes, bootstrap arms one or more ungated daily wake times (always_run). Default is a single wake at 09:00; an operator can add more in the Advanced panel (e.g. 09:00, 13:00, 17:00) — each is a guaranteed full pass regardless of change. This is the liveness floor beneath the gated pollers.

4.6 Recording a skip

A skip still creates a turn record so it is a first-class, auditable object in the turns table and dashboard — but a terminal one with no LLM call:

  • turns.status = 'skipped', skip_reason = 'nothing_changed';
  • the probe snapshot: which of the five sources were checked, each source's count-since-baseline, and the last_ran_at baseline used;
  • inbound_events.processing_status = 'skipped'; one audit row per skip.

The dashboard collapses consecutive skips into one strip — e.g. "⤳ 12 recurring wakeups skipped (nothing changed) · 08:00–14:00" — that expands to the individual firings and their snapshots. Real turns stay legible; skips stay auditable. Expanding a skip shows exactly why it was safe: "0 new events · 0 task changes · 0 approvals · 0 watched-resource changes · 0 delegated returns since 08:30."

4.7 Budget

Skips do not draw against max_wakeups_per_day — that counter meters real (LLM-running) turns only. Charging empty wakeups would defeat the feature and could starve an agent out of real work. This exclusion must be stated in the max_wakeups_per_day documentation itself, so it isn't later "fixed" into counting skips. Runaway protection stays with max_pending_timers (arming) plus per-skip auditing (a runaway probe loop is visible in diagnostics even though it's unmetered).

4.8 Configuration

The gate and the daily floor are universal, on-by-default runtime behavior. Every knob is overridable per agent in an Advanced configuration panel on the agent's settings (operator-facing, tucked away — not a routine control):

KnobDefaultEffect
Change-gatingOnOff = every recurring wakeup runs a real turn (legacy behavior).
Guaranteed wake times["09:00"]Ordered list of ungated daily wake times; add/remove entries.
Change sourcesAll five onToggle which of the five signals count for this agent.

Plus a per-timer escape hatch: schedule_self(..., always_run: true) opts an individual recurring timer out of gating (the compliance "prove you're alive" tick).

4.9 Schema (additive)

  • agent_timers.last_ran_at TEXT NULL — per-timer baseline; stamped only on a real run.
  • agent_timers.always_run INTEGER NOT NULL DEFAULT 0 — per-timer gate opt-out.
  • inbound_events.processing_status — add 'skipped' to the CHECK set.
  • turns — add 'skipped' status, skip_reason TEXT NULL, probe_snapshot_json TEXT NULL.
  • ai_employees — per-agent advanced config: change_gating_enabled, guaranteed_wake_times_json, change_sources_json.
  • Indices to keep the five count-since-last_ran_at probes cheap (most already exist on received_at / status columns).

6Open questions

  • Already-processed inbound events (source 1). An inbound event fires its own trigger-1/2/3 turn. Should it also count as "change" for a later recurring gate? Leaning yes (the review may want to synthesize across the day) — but a chatty agent would then almost never skip. Confirm, or restrict source 1 to unprocessed events.
  • due_at crossing detection (source 2). A task becoming due is time passing, not a row insert. Leaning compute-at-probe (tasks with last_ran_at < due_at ≤ now) rather than materializing a task-due event. Confirm.
  • Skip-strip aggregation. Collapse consecutive skips per-timer or across all of an agent's timers? UI detail, but affects how the strip reads. Leaning per-agent, expandable to per-timer.
  • Timezone for guaranteed wake times. Reuses the autonomy spec's open decision (workspace tz, fall back to UTC). Confirm no separate per-agent tz here.
