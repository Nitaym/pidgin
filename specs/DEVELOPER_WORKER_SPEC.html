Feature Spec

Developer Worker

Two hired workers that carry a Linear ticket from idea to merge: a Team Lead that scopes the ticket and turns review comments into tasks, and a Developer that runs Claude Code on it in its own branch, posts a live build for the owner to test, and merges once the owner approves.

Draft Author: Nitay (drafted by Claude) 2026-11-07 · updated the same day with the owner's ticket flow (Team Lead, review builds, merge policy)

1Summary

The owner already works with coding agents through Linear tickets: an agent claims a ticket, comments, commits with the ticket id and hands off through a Needs owner status. Today a person has to open a Claude Code session for every ticket. The Developer Worker closes that gap inside Pidgin. The owner hires a Developer, connects Linear with the API key of a dedicated Linear member (so the worker acts as "Claude", never as the owner), points it at a local repo, and sets its rules. Next to it sits a Team Lead, a second hired worker with its own Linear member, so the assignee column always says whose move it is: Lead, Dev or owner.

A ticket assigned to them goes through fixed phases (§4.1). The Lead scopes it: it enriches the ticket until it is self-contained and asks questions in comments, handing the ticket to the owner while a question waits. The owner approves the scope by moving it to Ready. The Dev reviews it, asks the Lead anything still unclear, then works it in its own git worktree on a branch per ticket with headless Claude Code. When done it deploys a review build the owner can play live and hands the ticket to the owner In review. The owner comments; the Lead turns the comments into tasks and the Dev goes again. Once the owner approves, the branch is rebased onto main and merged automatically, and the ticket is Done. Two rules hold throughout: status = phase, assignee = whose move, and a failed run goes back to the Lead, not the owner.

It is four new pieces on top of what Pidgin already has: a Linear connector; a Linear watcher that polls (the PC is behind NAT, so no webhooks) and writes change rows the existing change-gated wakeup reads; a Claude Code executor that runs, caps, logs and recovers coding runs (and deploys review builds and merges); and two recipes, team lead and developer, with each role's rules. The owner sees and steers the work in both places: in Linear (scoping questions, claims, progress, review links, as comments from the Lead and the Dev) and in Pidgin (a work dashboard, a review page per ticket, a page per run with its live log, Stop and Retry, approvals and spend). Trackers and coding agents are behind generic seams, so GitHub Issues or Codex can be added later as one more connector or executor.

2Scope

In scope

  • Owner experience: hiring a Team Lead and a Developer, connecting Linear with a dedicated member for each, choosing a repo, setting rules; the work dashboard, review page, run page, logs, Stop/Retry; hand-offs and approvals in Linear and in Pidgin.
  • The ticket flow (§4.1): phases as Linear statuses (Scoping → Ready → In Progress → In Review → Approved → Done), assignee as whose move, questions that flip the assignee and back, the owner's two approvals (scope and result), skipping phases by setting a status, and the failure path back to the Lead.
  • A team_lead recipe: scopes tickets until they're self-contained, answers the Dev, escalates to the owner only what it can't answer, turns review comments into tasks, retries failed runs up to a limit.
  • Review builds: a deployed build of the ticket's branch the owner can play live, linked from the ticket with what changed and what wasn't verified.
  • Automatic merge after the owner's approval: rebase onto main, test, fast-forward or rebase-merge (never a merge commit); hand back to the Lead on conflict or failing tests.
  • A linear connector: reads (tickets, inbox, comments, team states/labels/members), writes (comment, status, assignee, labels, new Triage ticket), API-key auth, health check.
  • A Linear watcher: outbound-only polling (a new-ticket check every 5 s, running tickets every 60 s, slowing itself when Linear's rate headers run low) that starts assigned work at once and writes change rows for the change-gated wakeup. This fills the "connector-side watcher" gap the change-gated wakeup and autonomy specs left out of scope.
  • Trigger rules per worker, on status + assignee (assigned to the Lead; Ready or handed back to the Dev; Approved; comments and mentions).
  • A claude_code executor: a dev slot switched to the ticket's branch (a worktree per ticket when there are no slots), prompt from the ticket, concurrency cap, never the same ticket twice, crash recovery by reconciling with Linear, failure handling with a runner-failed label, logs, token usage.
  • Ticket tools handed to each run (a small MCP server scoped to that one ticket), so Claude Code talks to Linear through Pidgin's gate without holding the key.
  • A developer recipe: review the ticket and ask the Lead, claim, comment progress, ticket id in commits, hand off In review with a review build, self-contained comments, the target repo's own CLAUDE.md and skills.
  • Generic seams: tracker connectors and coding executors as registries.

Out of scope

  • Webhooks, relays and Linear's app-actor "agent" API: they need a public endpoint; this PC is behind NAT.
  • Releasing: store builds, production deploys and release notes. Review builds are previews of one branch; merging into main happens only after the owner approves the review.
  • Other trackers and executors (GitHub Issues, Jira, Codex, Aider): the seams are designed now, built later.
  • Cloud or remote execution: runs happen on the owner's machine, against a local clone.
  • Multi-repo tickets: one worker works one repo in v1.
  • Agent-to-agent delegation beyond the ticket: the Lead and the Dev talk only through the ticket (comments and assignee), never through a private channel, so every exchange is visible in Linear.
  • Backlog planning: the Lead enriches tickets it's given; it doesn't groom or prioritise the backlog, and files new work only in Triage.
  • The richer v2 dashboard (queue board, diff viewer, cost charts, Slack notices); see §9.

3Why this exists

The owner runs a game studio repo (ActualGameplay) where every task is a Linear ticket, and agents already follow a ticket discipline written into the repo's tickets skill: claim (status In progress, assigned to Claude, a Started: comment), comment when something real happens, put the id at the end of each commit subject, finish as Done or hand off as Needs owner assigned to the owner, file new work in Triage, and pick up agent-ready tickets when working alone. The owner created a dedicated Linear member, Claude (claude@gravitize.co.il), so agent work is never attributed to them.

What's missing is the trigger. Assigning a ticket to Claude does nothing until a human opens a Claude Code session and says "take ACG-123". The goal: assign it, walk away, come back to a hand-off. Existing tools were reviewed and none fit: Cyrus needs webhooks or a relay; a bash gist (dylancwood) polls a label and runs claude -p in worktrees but is Unix-only; Reeve (ianchenx/reeve) is a small self-hosted daemon whose crash-recovery ideas are borrowed here. Pidgin already has the hard parts (connectors, recipes, change-gated recurring wakeups, approvals, autonomy, token tracking), so the worker belongs in Pidgin as a hired role.

4Owner experience

4.1 The ticket flow

Every ticket is shared by two hired workers and the owner. The Team Lead scopes it, answers the Dev, and turns review comments into tasks. The Developer writes the code, deploys a review build and merges. The owner answers questions and approves twice: the scope (Ready) and the result (Approved). Both workers are Pidgin personas with their own recipe and their own Linear member, so Linear's assignee column shows Lead, Dev or owner at a glance.

Status = phase. Assignee = whose move. A question never changes the status. It reassigns the ticket to whoever must answer (the Dev asks the Lead; the Lead asks the owner), and the answer reassigns it back. The owner's "waiting on me" view is simply "assigned to me", across every phase.

4.1.3 When a run fails, and review rounds

  • Failure goes to the Lead, not the owner. A Dev run that crashes, times out or gets stuck (no output, turn limit) leaves the ticket In Progress, assigns it to the Lead, and comments the reason, the last step and the log link. The Lead may retry up to a configurable limit (default 2 retries), each a fresh run on the same branch with the failure in the prompt. Past the limit it re-scopes (back to Scoping with what it learned) or asks the owner (assigns the owner with a question). The owner's Retry button in Pidgin still works at any time and doesn't count against the limit.
  • Review rounds keep the Dev's session (the owner's choice). When the Dev finishes (step 9) the run ends and frees its slot; nothing sits waiting for the owner. The run record keeps the Claude Code session id. When the ticket comes back from review (step 11 → 6), the executor resumes that same session (claude -p --resume <session-id>, in the same worktree and branch) and passes it the Lead's new comment, so the Dev remembers its earlier reasoning. If the session can't be resumed (its transcript is missing, e.g. deleted or on another machine), the executor falls back to a fresh run that reads the ticket thread and the branch (commits and diff against main), and says so on the ticket ("Couldn't resume the earlier session; started fresh from the ticket and the branch."). That's why the Lead's step-11 comment must still be self-contained: it has to be enough for the fallback.
  • Questions end runs. A Dev run that needs an answer posts it with ticket.ask_lead and ends; nothing sits waiting on a live process. The answer starts a fresh run that reads it in the thread.

4.1.4 The review: what the owner gets

The review link is a deployed build of the ticket's branch that the owner can play live, on a phone or a desktop, not a diff. The repo entry configures how to deploy (a review deploy command and the URL pattern it produces; §5.5.9). For ActualGameplay it is the game's page from that branch, with direct links such as ?level=6 (0-based) and ?bot=1&level=6 where the change is level-specific. The Dev's In review: comment holds, self-contained:

  • Play it: the build link, plus one direct link per thing to check (level, bot, screen).
  • What changed: each change as the player sees it, in one line, with the ticket's "Done when" lines ticked or not.
  • Not verified: what the Dev couldn't check (feel on a real phone, art it didn't have, a device it couldn't run), so the owner knows where to look.
  • Tests and bot: what ran and the result.
  • Branch: name, commits on top of main, round number.

Pidgin shows the same on a review page per ticket (/{workspace}/agents/{id}/review/ACG-131): the build with a QR code for the phone, the comment's sections, the diff summary and commits, the runs of every round, and two buttons that act in Linear: Approve (sets Approved) and Request changes (posts the owner's comment, which wakes the Lead).

4.1.5 Merge policy

  • A branch per ticket, reused by every round and retry.
  • Merge only after the owner's approval (status Approved), and then automatically: the owner never has to run git.
  • Never merge without rebasing first. The executor fetches, rebases the branch onto the latest main, runs the repo's test command, and only then merges by fast-forward or rebase-merge. History stays linear: no merge commits, ever.
  • PR then merge. The branch is pushed and a pull request opened (it records the review and the link), then merged with the rebase method. Where the repo has no remote, the local main is fast-forwarded instead.
  • If the rebase conflicts or the tests fail after rebasing, nothing is merged. The ticket goes back to In Progress, assigned to the Lead, with what conflicted or failed; the Lead turns it into a task for the Dev (the retry limit applies).
  • After the merge: Done, the review build is taken down, and the worktree is cleaned up. The branch is deleted only on the remote after the PR merges, as the host normally does.

4.2 Hiring a developer

The Developer is a bundled role template ("Developer" in the hire picker; UI never says "recipe"). It uses the normal hire wizard and HR assist panel (Hire UX) with one extra step, Workplace, that ties the hire to a tracker, a repo and rules. The wizard won't let the hire go active until both integrations are healthy and the repo checks pass (warnings are allowed, errors aren't).

Two hires, one team. The Team Lead ("Team Lead" in the hire picker) is hired the same way, with its own Linear member (e.g. "Claude Lead"). Hiring either one offers to hire the other, and they're paired: the Developer names its Lead, and the Lead names its Developer(s). One Lead can serve several Developers on the same team and repo. The Lead's Workplace step has the same tracker, team and owner fields but no repo checks of its own; it reads the repo (read-only) through its Developer's repo entry, so it can quote files into tickets.

  • Name. Prefilled from the Linear member's name (viewer.name, e.g. "Claude"), so the worker's name in Pidgin matches the author of its comments in Linear.
  • Linear team(s). Picked from the connected workspace (v1: one team, e.g. ActualGameplay, key ACG).
  • Owner in Linear. The owner's Linear account (e.g. Nitay). Hand-offs are assigned to it, and it is mapped to the owner's Pidgin principal so the gate knows its assignments and comments are commander instructions (§5.7). More commanders can be added.
  • Repo. One of the repos registered on the Claude Code integration, or "Add repo" inline.
  • Rules. §4.5, with defaults that match the owner's existing ticket conventions.

4.3 Connecting Linear as a dedicated member

Linear is a normal integration with its own setup page (/{workspace}/integrations/linear, per Connectors §8). The owner signs in to Linear as the dedicated member, creates a personal API key (Settings → Security & access → API keys), and pastes it into the Manual tab. Pidgin runs the health check and shows who the key belongs to. The Lead and the Developer each need their own member and key (one Linear installation per worker), because the assignee is how the flow says whose move it is; two workers on one member would make "assigned to Claude" ambiguous. Two guard rails:

  • Wrong account. If the key's email matches a principal marked as a commander (the owner), the page shows an error-style banner: "This key belongs to Nitay. The developer would act as you. Use the developer's own Linear member." Hiring is blocked until it's fixed (an explicit "use it anyway" exists for single-person setups).
  • Seat and access. The health check also lists the teams the member can see; if the chosen team is missing, it says "Add Claude to the ActualGameplay team in Linear."

4.4 Pointing it at a repo

Repos are registered on the Claude Code integration page (a local executor is an integration like any other: health check, status, disconnect). Each repo entry holds: path, base branch (default: the repo's current branch, usually main, used as a local ref because the owner commits locally), worktree folder (default under the Pidgin home, never inside Dropbox/OneDrive), setup command, and branch-name pattern. The Claude Code health check runs claude --version and a tiny headless call to confirm the CLI is installed and signed in.

5.3 Trigger rules

The watcher evaluates these on every poll against the current state of the team (level-based, so a missed poll can't lose a ticket) and writes a change row only when a ticket newly meets a rule, keyed so the same change is never recorded twice. The executor checks rules 2, 3 and 5 again against live Linear right before it claims or merges (§5.5.2).

Rules are written against status + assignee (§4.1). Shared exclusions for every rule that starts work: no owner-only or runner-failed label, no open "blocked by", no active or queued run for the ticket.

Owner-only statuses. Ready and Approved count only when a commander set them (the watcher reads the actor from the issue history). If a worker or a teammate sets one, the worker comments "Only the owner approves; moved back" and restores the previous status. Skipping phases is just the owner setting a later status; the rules above pick the ticket up from there.

What never starts work. Moving a ticket to Todo on its own: a ticket assigned to neither worker is not for them, however it got there. Also never: changes made by the worker itself (the watcher ignores its own actor id, so its own claims and comments can't loop; the Lead and the Dev do see each other's changes, which is how they hand over), other teams, and anything labelled runner-failed until the owner removes the label or presses Retry. Whether unassigned agent-ready tickets still feed the flow is open (§8).

Interactive sessions also act as Claude. The owner's hand-opened Claude Code sessions sign in to Linear as the same member and claim tickets the same way. The worker treats only tickets with its own code_runs record as "its runs". A ticket an interactive session has In Progress is never touched by recovery (§5.5.6), and it triggers nothing unless it is moved to Ready or Approved by the owner.

5.4 Linear watcher

  1. Where it runs. A new pidgind component, the Poller, next to the Scheduler (Agent Runtime §9.1 lists a "watcher dispatcher" that receives connector-side change notifications; for connectors that can't push, this is it). It ticks every few seconds and polls each active watch whose interval is due.
  2. What it polls. The worker's agent_watchers rows on poll-capable resources. Each worker arms its own at bootstrap: watch("linear:queue/ACG") and watch("linear:inbox/me"), read through its own Linear installation, so "me" is the Lead for the Lead and the Dev for the Dev. Using real watcher rows keeps change-gating's rule that only explicitly watched resources count (Change-Gated Wakeup §4.2, source 4).
  3. Per poll (one request, small aliased pages, every 5 s by default): the open tickets assigned to the worker, plus (for the Dev) Ready and Approved tickets in the team, with the last status change's actor; tickets with active runs (rule 6); notifications since the inbox cursor (rule 4).
  4. Diff. Results are compared with a local mirror (tracker_items) and a seen-set keyed by (ticket, rule, Linear updatedAt or comment id). New entries become change rows; the mirror and cursor advance in the same transaction, so a crash mid-poll re-reads rather than skips.
  5. Change rows. One inbound_events row per change: trigger_type = 'watcher', processing_status = 'recorded' (new status: never dispatched on its own), trust label from the actor (§5.7), normalized payload (Connectors §6) plus {kind, ticket_key, ticket_id, actor, comment_id?}.
  6. Waking the worker. At bootstrap the worker arms a recurring work queue timer (interval, default every 2 min). The existing change-gate probes it: source 4 counts the recorded rows since the timer last ran; zero means a free skip, non-zero means a real turn. That turn's context lists every recorded row since the last real run (a batch: ten ticket changes cost one turn, not ten); they are then marked done with resulting_turn_id.
  7. Fast path for assignments. Assignment is the one change that doesn't wait for the timer. A ticket assigned to the Dev that qualifies under its rules is claimed and started by the executor in the same pass that saw it (no turn, no next loop); one assigned to the Lead dispatches the Lead's turn at once. From assignment to Claude's first output is about 10–15 s: up to one 5 s check, ~1.5 s of Linear calls (claim fetch, claim), under a second to put a dev slot on the branch, and ~5–6 s for Claude Code to start and answer (measured 2026-11-07). Each run records when the ticket was last touched, when it was seen and when Claude first answered, and the Work page shows "started in 11 s" per run. Comments and mentions still batch on the timer.
  8. Liveness. The last successful poll time is shown on the dashboard; errors back off and surface on the integration page (§5.2).

5.5 Claude Code executor (claude_code)

A local executor, registered as an integration (connector_type = "claude_code") so it reuses the registry, health check, integration page, gate and audit. Its config holds the machine-wide cap and the registered repos. The developer starts work with execute(resource="claude_code:repo/actualgameplay", payload={ticket: "linear:issue/ACG-131", mode: "start" | "follow_up" | "retry" | "merge", note?}). Only the Dev calls start, follow_up and merge; the Lead may call retry (counted against the retry limit) but never writes code itself. Keeping it an execute preserves the locked 14-action vocabulary (open question §8).

5.5.2 Admission: cap and never twice

  • Never the same ticket twice. A unique partial index on code_runs(ticket_id) where status is active (queued, claiming, preparing, running) makes a second start impossible at the DB level; a duplicate execute returns the existing run.
  • Cap. A run starts when the worker has fewer than its cap running and the machine is under the integration-wide cap. Order: merge class first (short, and it unblocks the owner), then follow-ups (answers, review rounds, retries), then new Ready tickets, each by priority then age.
  • Claim with a re-check. Right before starting, the executor re-reads the ticket live. Still eligible (Ready for a start; In Progress assigned to the Dev for a follow-up; Approved for a merge) → one execute (status + assign the Dev) and, for a start, one post (Started: line from the turn's plan, plus the run link). Moved, reassigned or relabelled meanwhile → dropped, logged, no comment.

5.5.3 Dev slot and branch

  • Branch: the pattern from the repo entry, default claude/{key}-{slug} (slug from Linear's branchName, lower-case). One branch per ticket, reused by follow-ups and retries.
  • Dev slot: runs work in the same reusable worktrees as the owner's dev terminals and the repo's own runner (<slots_dir>/slot-N, sparse, outside Dropbox, each game's node_modules kept), so switching branches is the only preparation. The executor takes a free slot with no uncommitted changes (the ticket's last slot first, so a review round can resume its session), writes the shared .agent/lock.json (mode pidgin-run, the ticket key, Claude's pid, so the slot stays taken across a Pidgin restart), and runs git switch <branch>, or git switch -c <branch> <base> from the newest of local and origin main the first time. The lock is removed when the run ends. With no free slot the ticket waits in the queue; a new slot is made only below the slot limit, and the setup command runs only in a newly made slot.
  • Without slots (the slots folder isn't this repo's): <worktree_root>/<key>, created with git worktree add -b <branch> <path> <base> and reused; the setup command runs once per new worktree.
  • The run sees the repo's committed CLAUDE.md, .claude/ skills and settings, because a worktree is a checkout. The hire-time check warns when the main checkout has uncommitted changes to them.
  • Cleanup: worktrees are kept after a run (the owner may want to look). They're removed when the branch is merged into the base, or after 14 days with no run, never while a run is active. The branch is never deleted by the worker.

  • Spawned detached in its own process group (on Windows CREATE_NEW_PROCESS_GROUP), with output going to files, not pipes, so a pidgind restart doesn't kill the run, and the run's state can be read back from disk.
  • The executor records PID and process start time (PIDs are reused on Windows), tails the stream file, and writes a heartbeat on the run row every 15 s while the process lives (Reeve's lease idea).
  • Stop kills the whole process tree (child shells, dev servers, test runners), not just the CLI.

5.5.6 Crash recovery: reconcile with Linear

On pidgind start, and every 5 minutes, for each run in an active state:

  1. Process alive (PID + start time match) → re-attach: tail the stream file from its last offset.
  2. Process gone, stream has a final result event → it finished while pidgind was down: finalize normally (outcome from the ticket tools' record, usage from the result).
  3. Process gone, no result → read the ticket: if it reached In Review, the Lead or Done through this run's ticket tools, finalize as that; otherwise treat as failed (reason "runner stopped unexpectedly") and run the failure path (§5.5.7).
  4. Queued/claiming rows → re-run admission; claiming re-checks the ticket, so a half-done claim is completed or dropped, never doubled.
  5. Orphan claims: tickets In Progress assigned to the worker that have a code_runs record but no active run → failure path. Tickets without a record (interactive sessions) are left alone.

5.5.7 Failure and timeouts

A run fails on a non-zero exit with no finishing tool call, a crash, the setup command failing, or any limit (time, silence, turns). The executor (not the LLM) then, in order: kills the process tree; keeps the worktree and branch; posts a comment ("Run failed: time limit after 60 min. Last step: running npm test. 2 commits on claude/acg-115-…. Log: <link>. Retry 1 of 2."); keeps the status; assigns the ticket to the Lead. The Lead's turn decides: retry (a fresh run with the failure in the note), re-scope (back to Scoping with what it learned), or ask the owner. The executor counts retries per ticket and phase and refuses a third retry from the Lead (default limit 2); past it the Lead must re-scope or ask, and if it gives up it adds runner-failed, which stops every rule until the owner removes it or presses Retry. A run that exits cleanly but never called a finishing tool ends ended_open and goes to the Lead the same way, so the ticket never sits In Progress with nobody on it.

5.5.9 Review builds and the merge

Review build. The repo entry gains a review deploy command and a review URL pattern (e.g. npm run review-deploy -- {branch} → https://…/review/{key}/), plus an optional review teardown command. When a run calls ticket.in_review, the executor runs the deploy command in the worktree (output in deploy.log), checks the URL answers, and only then posts the run's In review: comment with the build link and moves the ticket to In Review, assigned to the owner. A failed deploy is a failed run (to the Lead). Each round redeploys to the same URL, so the link in the ticket stays valid. Without a configured command, the comment says "no review build: this repo has none set up" and links the branch, so the owner is never handed a dead link.

Merge (rule 5, owner set Approved), run by the executor with no LLM in the loop:

git fetch origin
git rebase origin/main            # in the ticket's worktree; conflict → abort, blocked
<repo test command>              # e.g. npm test in the touched packages; failing → blocked
git push --force-with-lease origin <branch>
gh pr create --fill --base main   # or reuse the open PR; body = the review comment + review link
gh pr merge --rebase              # linear history: no merge commits
                                  # no remote configured: fast-forward local main instead (git merge --ff-only)

On success: a Merged: comment (PR, commit on main), Done, the teardown command removes the review build, the worktree is removed. On blocked: nothing is merged; a Not merged: comment with the conflicting files or the failing tests, In Progress, assigned to the Lead (counts as a failed run for the retry limit). Pushing and opening the PR happen only here, after the owner's approval; the run itself can't push (§5.5.5).

5.6 Ticket tools inside a run

A headless run can't do an interactive Linear sign-in, and handing it the API key would break "agents never hold credentials". So each run gets a tiny local MCP server from pidgind, scoped to its one ticket, whose calls go through the same gate and connector as the worker's own actions and land in agent_action_log:

ToolDoes
ticket.readRe-reads the ticket and comments (to see replies mid-run).
ticket.comment(body)Posts a progress comment. Rate-limited (default ≤1 per 5 min, ≤10 per run) so a chatty run can't spam the ticket.
ticket.in_review(play, changed, not_verified, tests)Hands the work to the executor's review step (§5.5.9): deploy, then the structured In review: comment with the build link + In Review + assign the owner. Ends as in_review.
ticket.ask_lead(question)Question for the Lead: comment + assign the Lead; status kept. Ends as asked. There is no tool that asks the owner directly.
ticket.done(summary)Only when the Lead's brief says no code change is needed (e.g. the answer was "already works"): comment + Done. Ends as done.
ticket.file_triage(title, body, labels)New ticket in Triage (same team), linked to this one.

The repo's own tickets skill tells interactive agents to use a Linear MCP and to check whoami; the run's rules say these tools replace that, and the tools already act as Claude. The commit-message rule and the self-contained rule stay the repo's own.

5.7 Trust and the gate

  • Who asked. Each change row carries the Linear actor who caused it (who assigned, who added who set a status, who commented), mapped to a principal. Linear users mapped as commanders (the owner, set at hire) produce internal-authenticated rows; other members of the Linear workspace produce external-verified; text inside tickets written by non-commanders is data.
  • The owner's approvals are statuses only a commander can set. Ready and Approved count only when the issue history shows a commander set them (§5.3). A teammate assigning a ticket to the Lead is staged for approval ("Sara assigned ACG-150 to Claude Lead. Scope it?"); a teammate can never approve a scope or a merge.
  • The Lead and the Dev are not commanders to each other. The Dev follows the Lead's tasks because the Lead's brief restates the owner's approved scope and the owner's review comments; text the Lead adds beyond them is treated as guidance within the approved scope. Each sees the other's comments as internal-authenticated (same workspace), not as the owner's.
  • Writes to its own tickets (claimed, running or handed off by it) are ungated; writes to any other ticket are staged for approval. This is the same resource-scoped two-tier rule the Operating Partner needs for its plan sheet; both should use one mechanism.
  • Pushing, opening the PR and merging need no separate Pidgin approval: the owner's Approved status is the approval. They run only in the executor's merge step, never inside a run.
  • The run itself can only touch Linear through the ticket tools, so a prompt-injected run can at worst comment on, or hand off, its own ticket.
